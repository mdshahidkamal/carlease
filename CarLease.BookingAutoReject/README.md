# Booking auto-rejection worker (non-production only)

The EventBridge Scheduler invokes an on-demand .NET Lambda event function. Each invocation fixes a UTC cutoff at its start and processes every booking with `PickupDateTime` strictly before that cutoff and status `PENDING_REVIEW` or `CONFIRMED`. Each PostgreSQL batch locks its rows, changes them to `AUTO_REJECTED`, and inserts history in the same transaction. The lock makes overlapping invocations and the API's conditional status update serialize; retries cannot create another history row for a booking already rejected. The cutoff is independent of the schedule's local timezone. Failures are logged without connection strings or secret values and rethrown for Lambda's asynchronous failure handling. A timeout reserve causes unfinished runs to fail rather than report success; previously committed batches are safe to retry.

## Non-production prerequisites

Do not create or recreate existing infrastructure, and do not change production. Verify the AWS account, region and database endpoint independently before making any change. An operator must confirm the following existing resources and permissions; their names alone do not prove their identity or configuration:

- Region `ap-southeast-2`, function `carlease-booking-auto-reject-nonprod`, existing execution role `carlease-booking-auto-reject-lambda-role`, log group `/aws/lambda/carlease-booking-auto-reject-nonprod`, SQS queue `carlease-auto-reject-nonprod-dlq`, and Scheduler schedule `carlease-daily-auto-reject-nonprod`.
- Existing non-production VPC subnets and security group can reach the non-production RDS endpoint and Secrets Manager (VPC endpoint or NAT). The execution role can read `carlease/nonprod/database-credentials`, decrypt it if needed, connect to the database, and write logs. The database user needs SELECT/UPDATE on `Bookings` and INSERT on `BookingStatusHistories`.
- The secret is a JSON object with nonempty `username` and `password` strings, as used by the API deployment. Configure non-secret Lambda environment variables `DB_HOST`, `DB_NAME`, and optionally `DB_PORT` (default 5432) from the verified non-production database. No password is stored in configuration or logs. `BATCH_SIZE` defaults to 100 and must be 1-10000.
- Before deployment, apply `backend/Data/migrate-booking-status-history.sql` exactly once to the verified non-production database using the team's migration procedure and a backed-up database. For a new empty database, `booking-schema.sql` already contains the table and index; do not run both. This migration adds a table and an index; plan for index creation and locking on large tables.

## Build and verification

Use the .NET 10 SDK. The worker targets Lambda `dotnet10` and references the existing API data model. Build with `dotnet build backend\CarLease.Api.sln -c Release`. Run `dotnet test tests\CarLease.Api.Tests\CarLease.Api.Tests.csproj -c Release`. PostgreSQL integration tests are skipped unless `CARLEASE_TEST_POSTGRES` is set to a **disposable test database** connection string; they create and drop a uniquely named schema and require schema creation privileges. Run those tests against PostgreSQL before deployment; SQLite cannot verify PostgreSQL locking semantics.

Package with `dotnet lambda package --project-location CarLease.BookingAutoReject --configuration Release --framework net10.0 --output-package <artifact.zip>` using Amazon.Lambda.Tools. Verify the package and perform a manual invocation in the actual Lambda runtime, including its shared-framework dependencies, before enabling the schedule. The handler is `CarLease.BookingAutoReject::CarLease.BookingAutoReject.Function::FunctionHandler`. Match the existing function architecture when building the artifact. Update only the existing non-production function through the approved deployment process; retain its existing role, networking and log group. Set an appropriate timeout (up to 900 seconds) and reserve enough concurrency for the database; monitor duration and backlog. The worker intentionally fails when it runs out of time, so arrange retries or operational re-invocation for large backlogs.

## Schedule and failure delivery

The existing Scheduler schedule must remain **disabled** during migration, deployment and manual tests. After those succeed, an authorized operator can configure/verify the existing schedule for `cron(5 0 * * ? *)`, timezone `America/New_York`, flexible time window off, and the existing function target. Scheduler uses local time and handles DST according to AWS Scheduler semantics. Verify its execution role can invoke the function and send **delivery failures** to the existing SQS DLQ.

Scheduler invokes Lambda asynchronously: successful delivery does not mean the worker succeeded. Separately configure/verify the existing Lambda asynchronous invocation failure destination (or Lambda DLQ) to use the existing SQS queue and ensure the Lambda role has the required `sqs:SendMessage` permission. Confirm retry and event age settings, encrypted queue permissions, CloudWatch Errors/Throttles and DLQ alarms. Do not silently overwrite an existing destination or unrelated settings. Verify failure delivery by a controlled non-production test, and ensure the DLQ consumer/runbook distinguishes Scheduler delivery failures from Lambda execution failures.

With the schedule still disabled, manually invoke the function on isolated non-production bookings covering expired pending and confirmed, boundary/future, and other statuses. A manual invocation processes **all** eligible bookings in the configured database, not just test records. Before invoking, confirm that effect is acceptable and that the database has been backed up. For example, run `aws lambda invoke --region ap-southeast-2 --function-name carlease-booking-auto-reject-nonprod --cli-binary-format raw-in-base64-out --payload '{}' response.json`, then inspect the CLI response for `FunctionError`, the response file and the CloudWatch logs. Do not treat HTTP 200 alone as success.

Check status and history contents, UTC timestamps, idempotent reinvocation, concurrent admin transitions, multiple batches, rollback on audit failure, timeout/retry behavior, logs, and DLQ delivery. Ensure no customer data or credentials appear in logs. Only after deployment and all manual tests succeed may an authorized operator enable the existing schedule using `aws scheduler update-schedule` with its existing target, retry policy, timezone and DLQ preserved. If deployment or validation fails, leave it disabled and investigate; do not treat a successful Scheduler delivery as a successful worker run.

## Rollback

Disable the existing schedule first, preserving its other settings, and wait for in-flight invocations to finish. Restore the previously verified Lambda code and configuration or repoint the existing alias to its prior published version. If this is the first deployment, keep the schedule disabled and disable invocations rather than deleting shared resources. Status changes already committed are not undone by a code rollback: use the audit history and an approved, concurrency-safe correction procedure to reverse only affected transitions if required. Retain the history table and its records; do not drop it or restore a shared database instance without an approved recovery plan. Confirm the restored function and schedule state before resuming operations.
